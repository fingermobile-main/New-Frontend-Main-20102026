Implementation Roadmap: Missing CommandBank Features

This roadmap outlines the technical architecture, schema requirements, and sprint milestones necessary to transition your existing foundation (auditTrail middleware, basic governance, and moderation queues) into the full STERCS_CommandBank_v1 execution engine.

Phase 1: Architectural Foundation & Ingestion Enrichment (Weeks 1–3)

Before high-level features can run, the base auditTrail middleware must be enriched to record the structural context needed for trace retrieval, touch mapping, and time-bucket analytics.

1. Schema & Middleware Extensions

Update the current ingestion schema to include boundary boundaries:

// Proposed enrichment interface for auditTrail events
interface AuditEventEnvelope {
  id: string;
  timestamp: string;               // ISO 8601 UTC
  service: string;                 // PhotoCredits, Storefront, BeatwaveNG, etc.
  zone: string;                    // Admin Zone, Developer Zone, All Franchise Nodes
  nodeGroup?: string;              // NorthRegion, CentralOffice, EastNode, WestHub
  actor: {
    userId: string;
    role: string;
    isRoot: boolean;
    ipAddress: string;
    userAgent: string;
  };
  event: {
    category: 'AUTH' | 'POLICY' | 'TRANSACTION' | 'MODERATION' | 'SYSTEM';
    action: string;                // grant_approval, file_change, payout, injection_attempt
    status: 'SUCCESS' | 'FAILURE' | 'BLOCKED';
    failureReason?: string;
  };
  context: {
    panelName?: string;            // Store, Forum, Trends, Gems, Admin
    modulesTouched: string[];      // e.g., ["AuthCore", "BillingGateway", "ProductCatalog"]
    entityId?: string;
    beforeStateSnapshotHash?: string;
    afterStateSnapshotHash?: string;
  };
}


2. Storage & Indexing Strategy

Standard relational lookups will time out on multi-day cross-platform searches.

⚬ Compound Indices: Create compound indices on (service, actor.userId, timestamp) and (zone, event.action, timestamp).
⚬ Partitioning: Implement monthly range partitioning on the raw event log table by timestamp.

Phase 2: Trace Reconstructor & Module Touch Tracking (Weeks 4–6)

Implements user forensics and administrative access inspection.

1. Session Trace Service (forensics.trace)

⚬ Objective: Power queries like Retrieve and format session trace from PhotoCredits for user Agent-571.
⚬ Execution Flow:
  1. Ingest service and userId.
  2. Query the indexed audit table for actor.userId == input.userId AND service == input.service.
  3. Run results through a formatting pipeline that calculates time-deltas between sequential actions, flags sudden IP changes (session hijacking), and outputs structured text (e.g., chronological tree or sanitized markdown log).

2. Module Touch Inspector (forensics.touch)

⚬ Objective: Power queries like What modules did the Store admin panel touch at 2:13 PM WAT?.
⚬ Execution Flow:
  1. Standardize user-supplied localized timestamps (e.g., WAT, UTC) to a normalized UTC evaluation window (T \pm 60\text{ seconds}).
  2. Query logs filtering by context.panelName == input.panel within that window.
  3. Aggregate and deduplicate the context.modulesTouched array to return the distinct micro-modules altered during that interaction.

Phase 3: Dynamic Window Reporting & Entity Reconciliation (Weeks 7–9)

Bridges the gap between raw tables and quantitative analytics, enabling post-incident diffs.

1. Temporal Aggregation Engine (gov.report, diag.nodes)

⚬ Objective: Power reports across rolling windows (12hrs, 24hrs, 48hrs, 7days, from X to Y) and node failure summaries.
⚬ Implementation:
  ⚬ Build a centralized time-parser utility (DurationParser) supporting strings like 12hrs, 7days, and explicit ranges (2026-09-01 to 2026-09-10).
  ⚬ Introduce pre-aggregated roll-up tables (updated via background workers every 15 minutes) for high-frequency metrics:
    ⚬ grant_approvals
    ⚬ failed_logins grouped by nodeGroup
    ⚬ failed_payouts grouped by nodeGroup

2. Post-Mortem State & Entity Scanner (recon.diff, recon.scan)

⚬ Objective: Identify unverified entities (NFT mints, refills, invoices) or balance mismatches after incidents (e.g., wallet sync outage, Flamingo dispute escalation).
⚬ Implementation:
  ⚬ Incident Registry: Create an incidents lookup table that records the exact start_time and resolution_time of known outages.
  ⚬ Integrity Evaluator: For any command targeting a post-incident state, query entity states created within T_{\text{incident\_start}} and T_{\text{incident\_end}} + \text{buffer}.
  ⚬ Filter for missing foreign keys, pending verification flags, or unmatched ledger entries.
